But there are critical data integrity risks:

1. Duplicate labs can be saved multiple times.
2. OCR/parser can assign incorrect collection dates.
3. Users currently cannot correct mistakes.
4. Incorrect dates corrupt timeline/history trust.

This task is focused ONLY on:
- duplicate protection

# GOALS

# REQUIRED FEATURES

## 1. Collection Date Correction (P0)

During lab review / confirmation flow:

Users must be able to:
- see the detected collection date
- manually correct it BEFORE saving

Requirements:
- editable field
- clearly labeled
- preserve Meridian styling
- validate reasonable date format
- do NOT allow impossible dates
- corrected date must persist to Supabase

IMPORTANT:
This is ONLY for collection date right now.
Do NOT implement full biomarker editing.

---

# 2. Duplicate Detection Before Save (P0)

Before saving confirmed biomarkers:

Check for likely duplicates using combinations such as:
- user_id
- marker_slug
- collected_at
- source_panel
- value

Goal:
prevent obvious duplicate uploads/saves.

---

## Expected behavior

If likely duplicates are detected:

Do NOT silently save duplicates.

Instead show a clear warning such as:
> “Some of these biomarkers may already exist in your history.”

Allow user to:
- cancel
OR
- continue intentionally

Do NOT fully block saving yet.

This is a soft protection layer for Phase 1.

---

# 3. Prevent accidental duplicate counts

History counts and panel totals should NOT inflate incorrectly because of accidental duplicate uploads.

If the same upload was repeated accidentally:
- counts should remain trustworthy
- snapshot/history should not look corrupted

Implement the safest lightweight approach possible without major architecture changes.

---

Goal:
